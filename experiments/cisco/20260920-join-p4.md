# P4 实验报告：Join 阶段会话模糊测试（2026-09-20）

计划依据：`docs/fuzzer-全链路化升级计划-20260920.md` P4——"Join 变异上设备（首次设备授权，1 天在环）"。
目标：C9800-fresh 192.168.10.201（C9800-CL 17.14.01），LB 闸门补丁在位、cfmgr 已还原原始字节、profile/global country CN。
执行：`python -m capwap_discovery_fuzzer.stage_fuzzer`（分支 `feature/session-fuzzing`，提交 `4beae52` + 本报告对应提交）。
原始数据：Ubuntu `~/projects/capwap_log/20260920_join_p4/`（各会话目录含 `session.jsonl` + `summary.json` + 运行日志）。

## 1. 运行模式

- **每轮独立 DTLS 会话**：Discovery 前奏（同 5 元组）→ 握手（等飞行闭合 + 1.5s 沉降）→ Join Request → 15s 等待 → 优雅关闭（stdin EOF → close_notify）；
- **retries=1**：非 ANSWERED 时换新会话重试一次。原因见 §3；
- 判定：Result Code（Type 33）/ alert（s_client 被服务端关闭）/ silence / disjoin（btrace 抽样核对）。

## 2. 基线（locked join-v1）

| 会话 | 轮数 | 结果 |
| --- | --- | --- |
| `base10` | 10 | **10/10 Result Code = 0** |
| `locked20` | 20 | 见 `locked20/summary.json`（同参数） |

base 变体 = 黄金参数（radio 0/1、model C9105AXI-C、Type 29=14400、join 时 126 码 0x0101、AP Domain "default"、全部 VSP），唯一逐轮变化是随机 Session ID 与源端口。

## 3. 调试中发现的三个环境事实（已固化进代码/runbook）

1. **同 5 元组压制**：固定源端口 5400 连发时，首轮 rc=0 后第 2–4 轮全静默（会话存活期内新握手被压制）；
2. **换端口严格交替**：临时源端口下近似"成功-静默-成功-静默"——静默轮的新 DTLS 会话替下一轮清场，20s 轮间隙不能消除（非时间型）；
3. **工程对策**：静默即换口重试一次（`retries`），attribution 不变；base10 由此达到 10/10。

## 4. 变体矩阵（14 变体 × 2 轮，`matrix/`）

| 变体 | 结果 | 归因 |
| --- | --- | --- |
| base | 2/2 rc=0 | 基线 |
| omit-126 | 2/2 rc=0 | **join 时 Type 126（监管域声明）不参与 join 准入**（E7 已知：真正生效的是 Config Status 的 VSP-126） |
| omit-169 | 2/2 rc=0 | AP Domain 元素缺失不拒（WLC 仅记 "AP_DOMAIN payload count is 0"） |
| **omit-37** | **2/2 alert** | **VSP（board options/RAD_NAME）为 join 必需**；缺失 → 应用层 alert |
| **omit-29** | **2/2 alert** | **Maximum Message Length 必需**（复现 E5 run69 的 "Failure decoding max message size"） |
| omit-53 | 2/2 rc=0 | Limited ECN 可省 |
| omit-30 | 2/2 rc=0 | WTP IPv4 Address 可省（join 阶段不校验） |
| maxmsglen-0 | 2/2 rc=0 | Type 29 **只查存在性不查取值** |
| maxmsglen-65535 | 2/2 rc=0 | 同上 |
| **radio-1base** | **2/2 alert** | **Radio ID 必须 0 基**（复现 E5 结论：slot 0 必须存在） |
| radio-type-b-a | 2/2 rc=0 | 类型位图 0x01/0x02 被自愈默认（E5 "INVALID radio type" 警告路径） |
| regdom-code-0 / FFFF | 2/2 rc=0 | join 时域码取值不校验（E7：Config Status 的域码才校验） |
| **boarddata-shift** | **2/2 silence** | 板数据子元素编号 +1 → 整消息静默丢弃；btrace 出现 **MAC 0000.0000.0000 的会话**（MAC 从被破坏的板数据解析失败），无回包、连接不关闭 |

## 5. btrace 抽样核对（`show logging process wncd to-file`）

- alert 轮（omit-37/omit-29/radio-1base）：`Internal Error, Phase: Join`（10:14:31–10:14:45 三条，与轮次时间窗吻合）；
- 接受轮：`Heart beat timer expiry, Phase: Join`（~32s 后，客户端已离场）；
- boarddata-shift 轮：`MAC 0000.0000.0000 ... Heart beat timer expiry`——证实 §4 最后一行：**消息未被拒，身份被解析为空**。

## 6. 结论与后续

1. P4 目标达成：锁定基线可靠（10/10），14 变体矩阵全部给出可归因判定，两个已知开关（Type 29、板数据编号）被 fuzzer 自主复现，另得 6 项新容差/语义事实；
2. 新事实已回写 runbook（§4 元素表补充"join 阶段不校验项"）与 conformance（无改动：这些是 WLC 实现行为，非 RFC 违规）；
3. 遗留：`rounds-per-variant` 提升到统计意义（±20/变体）需要批处理优化——静默轮成本 25s，200 轮约 1.5h；建议 P5 起用"变体×N 轮"单会话重试策略并加 `--stop-after-silence` 之类的早停；
4. 数据文件：`experiments/cisco/20260920-join-p4/`（base10/locked20/matrix 的 summary+jsonl 副本）。
